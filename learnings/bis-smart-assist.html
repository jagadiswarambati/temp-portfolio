02 / WHAT I LEARNED

What I am learning so far.

These are working principles for the build, not claims about what is finished.

LESSON / 01

Domain information needs traceability

Standards-related answers should keep their source context close. A concise explanation is useful, but it should not cut the connection to the underlying material.

LESSON / 02

Plain language must preserve meaning

Making technical material easier to read is not the same as simplifying away important definitions, boundaries or conditions.

LESSON / 03

Evaluation needs real questions

A prototype can look convincing on a hand-picked example. Testing needs realistic user questions, ambiguous queries and cases where the source does not contain an answer.

LESSON / 04

Scope is part of engineering

For a build in progress, a clear user path and trustworthy behavior matter more than presenting every possible feature as done.

TECHNICAL CONCEPTS

Source-grounded answers

Pairing an explanation with the passage it came from. RAGSphere, elsewhere in this portfolio, is where I explored this idea in depth.

Handling unsupported questions

Distinguishing what the source supports from gaps or ambiguity, instead of guessing.

Evaluation design

Defining realistic questions and expected source references before judging quality.

Product scoping

Choosing one trustworthy user path first, and being clear about what is not built yet.
